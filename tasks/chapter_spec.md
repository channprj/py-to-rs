# 집필 스펙 (Authoring Spec) — 모든 챕터 공통

> 이 문서는 22개 챕터를 일관된 톤·구조·깊이로 확장하기 위한 단일 기준이다.
> 각 챕터를 집필/확장하는 사람(또는 서브에이전트)은 반드시 이 스펙을 따른다.

## 0. 책의 정체성

- **제목**: Python to Rust Complete Guide — 파이썬 개발자를 위한 러스트 마스터클래스
- **타겟 독자**: 10년 차 이상의 Python 백엔드/데이터/인프라 엔지니어 (CS 전공 지식 보유).
  - 메모리 구조(스택/힙), 포인터, 동시성, 다형성, 시간복잡도를 이미 안다.
  - `asyncio`, `multiprocessing`, `Pydantic`, `FastAPI`, `numpy`, `pandas`를 실무에서 써봤다.
  - "Hello World"식 설명은 모욕이다. 깊이로 존중하라.
- **핵심 컨셉**: 문법 나열이 아니라 **"Python 코드와 1:1 대응 + 내부 메모리 구조/디스패치/어셈블리 관점의 비교"**.
- **분량 목표**: 전체 A4 ~600페이지. 챕터당 평균 8,000~11,000 단어(한국어 기준), 약 25~30페이지.

## 1. 목소리(Voice)와 문체

- 한국어로 집필. 기술 용어는 **한국어(English)** 병기: 예) **소유권(Ownership)**, **단일형화(Monomorphization)**.
- 경어체("~습니다"). 단정적이고 자신감 있게. 군더더기 없이.
- 독자를 "여러분" 혹은 호명 없이 직접 대화하듯. 가끔 도발적인 질문으로 시작("~해본 적 있나요?").
- 과장된 마케팅 표현 금지. 대신 **근거(벤치마크 수치, 메모리 바이트, 어셈블리, 컴파일러 에러 메시지)**로 설득.
- 이모지는 절제(섹션당 0~1개, 경고 🚨 / 핵심 💡 정도만).

## 2. 챕터 표준 구조

각 챕터는 다음 골격을 따른다(섹션 개수는 주제에 맞게 조정하되 최소 5개 이상의 `##` 절):

```
# Chapter N. 제목  (기존 제목 유지)

(도입부: 3~5문단. Python 개발자가 이 주제에서 실무적으로 겪는 고통/한계를
 구체적 시나리오로 제시 → Rust가 이를 어떻게 다르게 바라보는지 예고.)

---

## N.1 The Python Way — 우리가 지금까지 해온 방식
(Python 코드 예제 + 그 방식의 런타임 비용/함정을 구체적으로.)

## N.2 The Rust Mental Model — 사고방식의 전환
(같은 문제를 Rust가 바라보는 철학. 왜 이렇게 설계했는가.)

## N.3 ~ N.k  핵심 개념별 심화
(각 절마다: Python 코드 → Rust 코드 → "Under the Hood" 박스로 내부 동작.)

## N.k+1 실전 예제 (Hands-on)
(현실적인 미니 프로젝트/리팩토링 시나리오. 컴파일 가능한 완전한 코드.)

## N.k+2 Best Practices & 안티패턴
(실무 체크리스트. "이렇게 하라 / 이건 피하라". clippy 경고 연계.)

## N.k+3 흔한 함정 (Python 개발자가 자주 하는 실수)
(Python 습관이 Rust에서 컴파일 에러/논리 오류로 이어지는 사례 + 해결.)

(맺음말: 1~2문단. 다음 챕터로의 연결.)
```

> 모든 챕터에 위 박스 이름을 그대로 쓸 필요는 없다. 하지만 **The Python Way → Rust Mental Model → Rust Implementation → Under the Hood**의 사고 흐름과 **실전 예제 + Best Practices + 흔한 함정**은 반드시 포함한다.

## 3. 필수 포함 요소 (각 챕터)

1. **비교표**: Python 개념 ↔ Rust 개념 매핑 표 최소 1개.
2. **Under the Hood 박스**: 메모리 레이아웃(바이트 단위), 디스패치 방식(static/dynamic), 또는 디스어셈블리 관점 설명 최소 2회. 마크다운 인용(`>`) 또는 굵은 소제목으로 표기.
3. **완전한 컴파일 가능 코드**: 핵심 예제는 `fn main()`을 포함해 그대로 `cargo run` 되도록. 발췌일 때는 `// ...` 로 명시.
4. **컴파일러 에러 시연**: 의도적으로 틀린 코드를 보여주고, 실제 `rustc`가 내뱉는 에러 메시지(`error[E0382]` 형태)와 그 해독을 최소 1회.
5. **벤치마크/수치**: 가능하면 Python vs Rust 성능 비교(현실적 배수: 보통 2~50배, 과장 금지). 측정 맥락(입력 크기, 빌드 모드 `--release`)을 명시.
6. **실무 크레이트 언급**: 해당 주제와 관련된 실전 크레이트(예: serde, thiserror, anyhow, tokio, rayon, pyo3) 소개.

## 4. 코드 스타일 규칙

- Rust 코드: `rustfmt` 스타일(4-space indent, snake_case). `edition = 2021` 기준.
- 코드 블록 언어 태그 정확히: ```python / ```rust / ```toml / ```bash / ```text.
- 주석은 한국어로, 핵심만. 코드 안에 "왜"를 설명.
- Python 코드는 타입 힌트 포함(독자가 시니어이므로). `from __future__ import annotations` 가정 가능.
- 에러/패닉 예시는 `// 🚨 컴파일 에러!` 또는 `// panic!` 주석으로 명확히 표시.

## 5. 일관성 규칙 (중요)

- **상호 참조**: "Chapter 4에서 본 소유권" 처럼 다른 챕터를 참조할 수 있다. 기존 챕터의 번호 체계를 신뢰하라(아래 챕터 맵 참고).
- 기존 챕터에 이미 있던 좋은 예제(Vector2D, 결제 상태 머신 등)는 **유지·확장**하되 삭제하지 말 것. 책 전체에서 동일 예제를 점진적으로 발전시키면 학습 효과가 크다.
- 도입부의 "다음 챕터 예고"와 맺음말의 "다음 챕터 연결"은 챕터 맵 순서에 맞춰라.
- 용어 통일: Ownership=소유권, Borrowing=대여, Reference=참조, Lifetime=수명, Trait=트레이트, Monomorphization=단일형화, Zero-cost Abstraction=무비용 추상화.
