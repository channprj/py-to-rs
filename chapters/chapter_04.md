# Chapter 4. 소유권 (Ownership): GC 없이 살아남기

파이썬 개발자로 살아오면서 메모리 해제 시점을 고민해 본 적이 있나요? 메모리릭이 터져서 `gc.collect()`를 호출해본 적은 있겠지만, 변수를 선언할 때 "이 변수는 언제 Heap에서 지워질까?"를 고민하며 코딩하는 파이썬 개발자는 없습니다. 

파이썬은 **Reference Counting(참조 횟수 계산)**과 런타임 가비지 컬렉터(Garbage Collector)를 결합하여 백그라운드에서 메모리를 청소합니다. 편리하지만, 이 청소부가 언제 깨어나 CPU를 멈출지(GC Pause) 모른다는 뜻이기도 합니다.

Rust는 이 GC를 완전히 없애버렸습니다. C/C++처럼 개발자가 `malloc`, `free`를 직접 호출하지도 않습니다. 대신 **소유권(Ownership)**이라는 3가지 규칙을 컴파일러가 강제하여, 스코프(Scope)를 벗어나는 순간 메모리가 *정확히 0초의 런타임 지연* 없이 해제되도록 설계했습니다. 이것이 Rust가 자랑하는 "런타임 제로 오버헤드"의 핵심입니다.

---

## 4.1 소유권의 3가지 규칙

Rust의 컴파일러(Borrow Checker)는 다음 세 가지 규칙을 무자비하게 검사합니다.

1. **Rust의 모든 값은 '소유자(Owner)'라 불리는 변수를 가진다.**
2. **특정 시점에 값의 소유자는 단 하나뿐이다.**
3. **소유자가 스코프(Scope)를 벗어나면, 값은 버려진다(Dropped).**

### 스택(Stack)과 힙(Heap)의 차이
규칙을 이해하려면 메모리의 종류를 알아야 합니다.
*   `i32`, `bool`, `f64` 처럼 크기가 고정된 데이터는 빠르고 복사하기 쉬운 **Stack**에 저장됩니다. 소유권 규칙을 몰라도 파이썬과 다를 바 없이 편하게 쓸 수 있습니다.
*   `String`, `Vec` 등 런타임에 크기가 변할 수 있는 데이터는 **Heap**에 할당됩니다. 소유권 문제는 이 Heap 데이터를 다룰 때 발생합니다.

---

## 4.2 Move Semantics: 얕은 복사도 깊은 복사도 아니다

파이썬에서 리스트를 다른 변수에 대입하면 어떤 일이 일어날까요?

* **The Python Way (Reference Assignment)**
  ```python
  list1 = [1, 2, 3] # Heap에 리스트가 생성되고, list1은 그 포인터를 가짐
  list2 = list1     # list2도 같은 Heap 주소를 가리킴 (Reference Count 1 -> 2)
  
  list2.append(4)
  print(list1) # [1, 2, 3, 4] 출력 (list1과 list2는 운명 공동체)
  ```
  파이썬은 단순히 메모리 주소(포인터)만 복사합니다. 이를 객체 참조(Object Reference)라고 부릅니다.

그렇다면 Rust에서 같은 코드를 작성해 봅시다. `Vec` (가변 배열)을 사용합니다.

* **The Rust Implementation (Move)**
  ```rust
  fn main() {
      // vec1은 Heap에 저장된 [1, 2, 3]의 유일한 "소유자"가 됩니다.
      let vec1 = vec![1, 2, 3]; 

      // vec2에 vec1을 대입합니다. 무슨 일이 일어날까요?
      let vec2 = vec1; 

      // println!("{:?}", vec1); // 🚨 컴파일 에러! "borrow of moved value: `vec1`"
  }
  ```

이것이 파이썬 개발자가 겪는 첫 번째 멘붕입니다. 에러 메시지는 **"값이 vec2로 이동(Move)했기 때문에, 더 이상 vec1을 사용할 수 없다"**고 말합니다.

**Under the Hood: 왜 이렇게 설계했을까?**
만약 파이썬처럼 `vec1`과 `vec2`가 같은 Heap 메모리를 가리키게 둔다면, `main` 함수가 끝날 때 (소유권 규칙 3번에 의해) 두 변수 모두 Heap 메모리를 해제(Drop)하려 시도할 것입니다. 이를 **이중 해제(Double Free) 버그**라고 부르며 C++에서 보안 취약점을 일으키는 가장 큰 원인입니다.

Rust는 아예 **"소유자는 단 하나뿐이다"**라는 2번 규칙을 통해, `vec1`에서 `vec2`로 변수를 대입하는 순간 `vec1`의 생명을 강제로 끊어버립니다(무효화). 이것을 얕은 복사가 아닌 **이동(Move)**이라고 부릅니다.

## 4.3 깊은 복사 (Clone)를 원한다면?

파이썬의 `copy.deepcopy()`처럼 Heap 메모리 자체를 두 개로 복제하고 싶다면, 명시적으로 `clone()`을 호출해야 합니다.

```rust
fn main() {
    let vec1 = vec![1, 2, 3];
    let vec2 = vec1.clone(); // Heap 데이터를 통째로 복사 (소요 비용 큼)

    println!("vec1: {:?}", vec1); // 이제 vec1도 살아있습니다.
    println!("vec2: {:?}", vec2);
}
```
파이썬은 대입 연산(`=`)이 얕은 복사인지 깊은 복사인지 상황에 따라 헷갈릴 때가 많지만, Rust는 값비싼 Heap 복사가 일어날 때는 코드에 무조건 `.clone()`이라는 꼬리표가 눈에 띄게 설계되어 있습니다.

## 4.4 함수로의 값 전달도 'Move'다

변수를 다른 변수에 대입할 때 뿐만 아니라, 함수에 인자로 넘길 때도 소유권은 이동(Move)합니다.

```rust
fn take_ownership(v: Vec<i32>) {
    println!("I took {:?}", v);
} // 여기서 함수가 끝날 때 v는 스코프를 벗어나고, Heap 메모리는 삭제(Drop)됩니다.

fn main() {
    let my_vec = vec![1, 2, 3];

    // my_vec의 소유권이 take_ownership 함수의 파라미터 v로 '이동'합니다.
    take_ownership(my_vec); 

    // println!("{:?}", my_vec); // 🚨 컴파일 에러! 이미 빼앗긴 소유권!
}
```

파이썬처럼 함수에 객체를 던져놓고 밖에서 또 쓰려면 어떻게 해야 할까요? 
매번 `clone()`으로 복사해서 넘기기엔 메모리와 성능 낭비가 너무 심합니다.

이 문제를 해결하기 위해 Rust는 객체의 소유권을 아예 넘기는 대신, **잠시 빌려주는 메커니즘**을 고안했습니다. 이것이 바로 다음 챕터에서 다룰 **대여(Borrowing)와 참조(Reference)**입니다.
